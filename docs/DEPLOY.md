# Деплой

Веб слушает `0.0.0.0` и порт `PORT` (по умолчанию 8000) сразу. Миграции идут рядом, под блокировкой, и не держат порт. `/health` отвечает 200, пока жив процесс. `/ready` отвечает 503, пока нет схемы или воркера. Без `DATABASE_URL` процесс сразу завершается с кодом 1. Подробности и откат — в `docs/DEPLOY_CHECK.md`.

Живые три окружения на Timeweb этим коммитом не создавались. Ниже то, как их развести, когда появятся отдельные боты.

## Окружения

| | dev | staging | prod |
| --- | --- | --- | --- |
| Бот | свой токен, long polling | свой токен и вебхук | свой токен и вебхук |
| База | своя | своя, копия схемы prod | своя, бэкапы включены |
| Домен | localhost | отдельный | `stimyl.online` сейчас смотрит на копию приложения |
| `SEED_DEMO` | `true` | `false` | `false` |
| `MAX_WEBHOOK_URL` | пусто | только у staging-бота | только у prod-бота |

Два процесса с одним `MAX_WEBHOOK_URL` перехватывают подписку друг у друга. Воркер и второе приложение эту переменную не получают.

Сейчас в Timeweb два приложения и одна база (`docs/TIMEWEB.md`, если файл есть локально). Это ещё не staging и prod. Для пред-прода нужна вторая база и второй бот.

## Первый запуск

1. Создать PostgreSQL 16 в том же регионе, что приложение. Пользователь приложения — не суперпользователь: отдельные `LOGIN` и база, права на свою схему, без `CREATEDB` и `SUPERUSER`.
2. Включить ежедневный бэкап в панели базы.
3. Собрать приложение из `main`. Команда сборки: `pip install .`. Команда запуска: `sh docker/entrypoint.sh`. Проверка: `/health`.
4. Переменные: `DATABASE_URL` с `sslmode=verify-full`, когда известен сертификат сервера. Пока в URL `ssl=require`, канал шифруется, сертификат не проверяется. Это записано предупреждением в лог.
5. `SESSION_SECRET` длинный случайный, не `change-me`. `COOKIE_SECURE=true`. `PUBLIC_BASE_URL=https://<домен>`. `ADMIN_MAX_IDS` — id админа в MAX. `SEED_DEMO=false`.
6. Флаги без нового деплоя кода: `FEATURE_PHOTO`, `FEATURE_OCR`, `FEATURE_QUIZ`, `FEATURE_LLM`, `TRAINING_AGGREGATE_TO_TEACHER`.
7. Деплой. Скрипт сам накатывает миграции и поднимает API.

Локально:

```bash
docker compose up --build
```

В compose у `db` и `api` стоит `restart: always`.

## Откат приложения

1. В Timeweb повторить деплой предыдущего `commit_sha` (`POST /api/v1/apps/{id}/deploy`).
2. Если новая миграция уже накатилась и старый код её не понимает, на staging выполнить `alembic downgrade -1`, проверить приложение, только потом повторять на prod.
3. Откат миграции не возвращает данные, которые новая версия успела удалить. Перед рискованным деплоем нужен свежий бэкап.

## Восстановление базы

Процедура, на staging в этом проходе не выполнялась:

1. Остановить приложение, чтобы оно не писало в восстанавливаемую базу.
2. В панели Timeweb создать восстановление из ежедневного бэкапа в новую базу или на тот же кластер по инструкции панели.
3. Подставить новый `DATABASE_URL`, задеплоить, открыть `/ready`.
4. Проверить, что учитель входит кодом, а число пользователей совпадает с ожидаемым.
5. Старую базу не удалять, пока проверка не прошла.

Подробности сбоев — в `docs/RUNBOOK.md`.
