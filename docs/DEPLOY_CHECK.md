# Проверка деплоя

На `main` это не выкатывается. Ниже — почему сборка `68fdef4` на Timeweb написала «No HTTP ports discovered, health check is disabled», и как теперь устроен старт.

## Почему не открылся порт

Timeweb ищет слушающий HTTP-порт вскоре после запуска процесса. Если сокета нет, проверка состояния выключается, трафик до приложения не доходит, бот молчит.

В `docker/entrypoint.sh` до этого исправления порядок был такой:

1. До 15 попыток `alembic upgrade head` с паузой 2 секунды. Пока база не ответила, `uvicorn` даже не запускался.
2. Потом сид, публикация команд и подписка вебхука — тоже до порта.
3. `uvicorn` поднимал приложение, а lifespan до приёма соединений ещё раз ждал `SELECT 1` и при ошибке ронял процесс.
4. Цикл `while` держал веб только пока жив воркер. Падение воркера убивало API.

Порт появлялся слишком поздно или не появлялся совсем. Сообщение про `russian_trusted_ca_bundle.pem` к этому не относится: это предупреждение `openssl rehash`, процесс из-за него не выходит.

## Что ждёт Timeweb

Проверено по документации App Platform (фреймворк FastAPI и деплой из Dockerfile):

| Способ | Порт |
| --- | --- |
| Фреймворк FastAPI, команда по умолчанию `uvicorn main:app --host 0.0.0.0` | **8000**. Порт в команде не указан, это порт uvicorn по умолчанию. Слушать нужно `0.0.0.0`, не `127.0.0.1`. |
| Явный `--port 80` | 80, если так записано в команде запуска. |
| Dockerfile | Порт берётся из `EXPOSE`. Если `EXPOSE` нет, платформа ждёт **8080**. |
| Переменная `PORT` | Её выставляет не платформа, а мы. Скрипт слушает `$PORT`, если она задана, иначе 8000. |

У этого репозитория в Dockerfile стоит `EXPOSE 8000`, команда запуска — `sh docker/entrypoint.sh`. Путь проверки в панели: `/health`. Это не `/ready`: `/ready` бывает 503, пока нет схемы или воркера, и платформа сочтёт деплой мёртвым.

`/health` отвечает 200, как только процесс жив, и отдаёт `version` — git SHA. Так видно, какая сборка работает. Если SHA не попал в окружение и в каталоге нет `.git`, в ответе будет `unknown`. Тогда в переменные приложения можно положить `GIT_SHA` равным выкатанному коммиту.

## Как стартует сейчас

1. `python -m app.boot` сразу пишет в лог версию, `ENV`, `DEV`, хост и порт и список недостающих обязательных переменных. Обязательна только `DATABASE_URL`. `DEV=true` при `ENV=prod` тоже ошибка. Секреты в лог не пишутся. При такой ошибке процесс заканчивается с кодом 1, не зависая на базе.
2. `uvicorn` слушает `0.0.0.0:$PORT` сразу. Lifespan не ждёт базу: порт открывается, `/health` уже 200.
3. Рядом, не блокируя порт: миграции (`python -m app.db.migrate`), сид, команда бота, вебхук. Миграции берут `pg_advisory_lock(874221)`. Второй процесс ждёт, а не пишет схему одновременно. Ошибка миграции остаётся в логе и не гасит веб.
4. Воркер крутится своим процессом. Если он упал, скрипт его поднимает снова. Веб из-за этого не убивается. Пока воркер не отметил heartbeat, `/ready` отвечает 503 с `reason=worker`.
5. После соединения с базой в лог пишутся применённые ревизии, статус базы (`up`/`down`) и TLS к `platform-api.max.ru` и `platform-api2.max.ru`. На `ENV=dev` проверка TLS пропускается. Ошибка TLS процесс не роняет: в `/ready` будет `warnings`, код ответа останется 200, если схема и воркер в порядке.

`/ready` отдаёт 503, пока нет соединения с базой (`reason=database`) или голова Alembic не совпала (`reason=migrations`).

## Сертификаты Минцифры

В настройках App Platform уже есть переключатель «Сертификаты Минцифры и ТЦИ». Для Dockerfile платформа сама кладёт в контейнер три файла, в том числе бандл `russian_trusted_ca_bundle` (в логе он может называться `.pem`). `openssl rehash` берёт только файл с **одним** сертификатом и пишет `skipping ... does not contain exactly one certificate`. Корневой и промежуточный файлы при этом ставятся. Своего шага `update-ca-certificates` в образе нет и не нужно: бандл в каталог rehash мы не копируем.

В репозитории один файл `certs/russian_trusted_root_ca.pem` — ровно один сертификат. `httpx` добавляет его через `SSLContext.load_verify_locations`, это не rehash. Если платформа задала `SSL_CERT_FILE` на свой бандл, стандартный `ssl.create_default_context()` использует его сам.

## Миграции 0004–0009 и код из main

`main` останавливается на ревизии `20261030_0003`. Ревизии `0004`–`0009` есть только на `feature/accounts`. Откат **кода** на `main` без отката схемы:

| Ревизия | Что делает | Код `main` |
| --- | --- | --- |
| `20261030_0004` | Таблица `jobs`. У `enrollments.status` и `user_sessions.csrf_token` стоит `NOT NULL` без значения по умолчанию. У демо-класса переписываются `join_key` и `join_code`, ключ `8b-demo` пропадает. | **Несовместима.** Старый код вставляет ученика в класс и сессию браузера без этих полей — вставка падает. Ссылка `8b-demo` больше не находит класс. |
| `20261031_0005` | На `sessions` добавлены `level`, `correct_streak`, `wrong_streak` с значениями по умолчанию. | Совместима. Старый INSERT эти колонки не трогает. |
| `20261031_0006` | `hint_step`, `task_misses`, `pending_step`, `pending_text`. | Совместима, те же умолчания или NULL. |
| `20261031_0007` | `state_version` со значением по умолчанию. | Совместима. |
| `20261031_0008` | `line_cursor`, `last_line` со значениями по умолчанию. | Совместима. |
| `20261031_0009` | `attempts.hinted` со значением по умолчанию. Проверка статуса темы расширена значением `started`. | Схема старые три статуса принимает. Строка со статусом `started` коду `main` непонятна: откат кода безопасен, только если таких строк нет. `downgrade` этой ревизии такие строки удаляет. |

Уже накатанные `0004`–`0009` не переписывались: менять применённую ревизию на живой базе нельзя. Новые ревизии дальше делаются добавлением колонок и таблиц. Удаление — только следующим релизом, когда предыдущий код уже не нужен.

## Откат

1. Снять бэкап базы в панели Timeweb. Пока снимок не готов, откат не начинать.
2. Откатить образ: в Timeweb задеплоить предыдущий `commit_sha` этой же ветки (`POST /api/v1/apps/{id}/deploy`). На `main` не переключать.
3. Открыть `/health` и сверить `version` с этим SHA.
4. Если новый код уже накатил ревизию, которую старый процесс не понимает (сейчас это `0004` для кода `main`, и любая будущая ревизия с `DROP` или `NOT NULL` без умолчания), на этой базе выполнить `alembic downgrade` до ревизии, с которой старый код умеет работать. Для возврата к `main` это `alembic downgrade 20261030_0003`. `downgrade` `0009` удаляет строки статуса `started`.
5. Снова открыть `/health` и `/ready`. `/ready` станет 200, когда схема совпадёт и воркер отметится.
6. Если `downgrade` не проходит или данные уже испорчены, поднять базу из бэкапа шага 1 и только потом запускать старый образ. Старую базу не удалять, пока вход учителя и число людей не сходятся.
